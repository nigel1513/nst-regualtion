# M7-G 법령·규정 구조 그래프 (Neo4j) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 현행 조항+참조선뿐인 보조 그래프를, 모든 dated 판본·조항 계층·계보·정확한 항 단위 참조·용어를 담은 법령 구조 그래프로 바꾸고, 그래프 RAG 확장·관계도·계보 API와 개정 영향 분석이 이것을 쓰게 한다.

**Architecture:** `reg.graph`가 PostgreSQL만 읽어 Neo4j에 투영한다(전체 재투영 + 규범문서 단위 증분, 증분 기준은 Work 노드의 지문 `fp`). 조회 함수(`reg.graph.query`)는 Cypher만 쓴다. API 라우터와 영향 분석(`reg.alerts.impact`)은 그 위에 얹는다.

**Tech Stack:** Python 3.12, psycopg 3, neo4j 5 driver, Neo4j 5.26 community, FastAPI, typer, pytest + testcontainers.

**Spec:** `docs/superpowers/specs/2026-10-03-graph-search-redesign.md` §0·§1·§3·§4

## Global Constraints

- `reg.graph`는 `reg.platform`·`reg.core`만 import한다 (`tests/test_architecture.py`).
- PostgreSQL은 읽기만 한다 (advisory lock `graph_lock`은 유지).
- UNWIND 배치 크기 5,000.
- `Provision.pv_id`, `Version.id`, `Work.id` UNIQUE; `Provision(path)`, `Provision(full_label)` 인덱스; `Term(name)` 전문 인덱스.
- 영향 분석 계약 유지: 심각도 표, `ALERT_CAUSE_PREFIXES = ("kr/law/", "kr/admrul/")`, 대상 없음(missing)·규범문서 전체(whole) 규칙.
- 운영 Neo4j는 GPU PC `bolt://192.168.0.2:8006`. 이 서버의 Neo4j(127.0.0.1:21064)는 건드리지 않는다.
- 테스트는 `nice -n 15`, pytest 한 번에 하나.

## Review Focus

1. 판본 사이에 공유되는 조항 판본(pv): 바뀌지 않은 항은 여러 판본·여러 부모 조에 속한다 → 기준일 확장·관계도가 다른 판본의 자식을 섞지 않아야 한다 (CONTAINS에 `versions`).
2. 대상 규범문서만 재적재(`rebuild_work`로 pv id가 모두 바뀜)된 경우 → 다른 규범문서에서 들어오는 참조선도 다시 만들어야 한다.
3. 참조 대상 경로가 출처 시행일 판본에 없을 때 → 현행 → 조 → 과거 판본 → missing 순으로 잇는다.
4. 정의 조항이 없는 규정, 따옴표 모양이 다른 정의(“ ” ‘ ’ " '), "라 함은" 형식.
5. 빈 그래프에서 증분 동기화 → 전체 재투영으로 처리.

## 모델 결정 (spec §1.1 해석)

- Provision 노드 = `provision_version` 1개. 속성: `pv_id, work_id, lineage(provision_id), path, parent_path, unit, label, full_label, heading, text, valid_from, valid_to(ISO 문자열, 열린 끝은 null), current(bool), version_ids(list)`.
- `(Version)-[:CONTAINS {ord}]->(top)`; `(Provision)-[:CONTAINS {ord, versions}]->(Provision)` — `versions`는 그 부모-자식 관계가 성립하는 판본 id 목록.
- 참조: `(Provision)-[:REL {evidence, resolution, review_status, target_path, match}]->(Provision|Work|MissingProvision)`, `match ∈ as_of|current|article|historical|missing|work`. REJECTED 참조는 넣지 않는다.
- `MissingProvision {key: work|path, work_id, path}` — 어느 판본에도 없는 대상.
- `Term {key: work|name, work_id, name, definition}`; DEFINES(정의 조 아래 `"X"이란 …을 말한다`/`"X"라 함은 …`), USES(같은 규범문서, 장·절 제외, 정의 조항 자신 제외).
- `Work.fp` = PG 지문(판본 id·상태·시행일, provision max id·수, reference max id·수·REJECTED 수, 제목·상태·기관). 증분 동기화는 지문이 다른 Work만.

### Task 4: 조회 (expand · neighborhood · lineage)

**Files:** Create `src/reg/graph/query.py`; Test `tests/test_graph_query.py`

**Interfaces:**
- `expand(driver, pv_ids: list[int], as_of: date | str | None = None, depth: int = 1, limit: int = 30) -> list[dict]` — 항목 `{pv_id, work_id, path, unit, label, full_label, heading, text, reason, rel, direction, via, hops, evidence}`; 이유: "예외 조항", "예외의 원칙 조항", "준용 대상", "근거 조항", "위임받은 규정", "위임한 조항", "시행 근거(상위) 조항", "시행 세부 조항", "인용 조항", "용어 정의: X", "상위 조문".
- `neighborhood(driver, pv_id: int, depth: int = 1, limit: int = 200) -> dict` `{center, nodes:[{id, kind, labels, props}], edges:[{source, target, type, props}]}`; id 형식 `pv:N`, `work:ID`, `ver:ID`, `term:KEY`, `missing:KEY`.
- `lineage(driver, pv_id: int) -> dict | None` `{lineage, work_id, entries:[{pv_id, path, label, full_label, heading, text, valid_from, valid_to, version_ids, change, from_pv, from_version, to_version}], deleted_in}`
