# 서비스 UI 개편 설계 (규정 대시보드 · 통합 챗봇 · 검수)

- 작성 2026-10-03 · 상태: 합의된 요구로 구현 진행 · 개정 알림 화면은 범위 밖(나중에 따로 논의)
- 사용자 요구 (원문 요지)
  - "규정 쪽 법령 나오는 게 대시보드 형태여야 하고, 본인이 원하는 기관을 선택해 조회하거나, 동일한 규정(예: 회계)을 검색하면 관련 모든 기관 것이 나와야 한다. 데모 페이지 같다 — 서비스 페이지다."
  - "질의응답과 검색은 같은 기능인데 사용 방법만 다르다 → 백엔드도 고치고 UI도 챗봇으로. 임베딩해서 OpenSearch에 넣었으니 그걸 기반으로."
  - "검수 쪽은 UI가 깨진 게 많고, 어느 기관 것인지 정보 없이 나와서 누가 뭘 해야 할지 모른다."

## 0. 공통: 서비스 수준의 앱 셸과 디자인 시스템

- 왼쪽 고정 사이드바(접기 가능, 모바일은 상단 메뉴): **대시보드 · 규정 탐색 · 주제별 비교 · 규정 도우미(챗봇) · 법령 · 검수** (알림은 메뉴에 두되 현행 화면 유지).
- 상단 바: **기관 선택기**(전체 / 25개 기관 + NST, 검색 가능한 콤보박스). 선택은 URL `?inst=KASI`와 브라우저 저장(localStorage, 실패해도 동작)으로 유지되고 모든 화면의 기본 필터가 된다.
- 디자인 토큰(`globals.css` :root, 다크 모드 포함): 색·간격·반경·그림자·타이포 스케일. 카드, 표, 배지(기관·종류·상태), 탭, 빈 상태, 로딩 스켈레톤, 오류 상태, 페이지네이션 공통 컴포넌트(`components/ui/*`). 아이콘은 lucide-react.
- 한국어 서비스 문구: 기술 용어(work, path, provision 등)를 화면에 노출하지 않는다. 날짜는 `2026. 10. 3.` 형식, 숫자는 천 단위 구분.
- 접근성: 키보드 이동, 포커스 표시, aria 라벨, 색 대비 AA.

## 1. 대시보드 (`/`)

| 영역 | 내용 | 데이터 |
|---|---|---|
| 요약 카드 | 수집 기관 수, 현행 규정 수, 조문 수, 최근 30일 개정 규정 수, 열린 검수 수 | `GET /api/v1/dashboard/summary?inst=` |
| 기관 현황 표 | 기관별 현행 규정 수·최근 개정일·최근 수집일·열린 검수 수, 행 클릭 → 그 기관 규정 탐색 | `GET /api/v1/dashboard/institutions` |
| 최근 개정 | 최근 개정·제정된 규정 20건 (기관 배지, 시행일) | `GET /api/v1/dashboard/recent?inst=` |
| 주제 분포 | 주제별 규정 수 막대 (클릭 → 주제별 비교) | `GET /api/v1/topics?inst=` |
| 바로 묻기 | 챗봇 입력창 (엔터 → `/assistant?q=`) | — |

기관을 고르면 대시보드 전체가 그 기관 기준으로 바뀐다.

## 2. 규정 탐색 (`/regulations`)

- 왼쪽 필터: 기관(다중), 주제, 종류(내부규정·법률·시행령…), 상태(현행·폐지), 최근 개정 기간.
- 본문: 규정 표(제목, 기관, 주제, 시행일, 조문 수, 상태) + 정렬 + 페이지네이션 + 제목 즉시 검색(자동완성: 기존 suggest).
- 규정 상세(`/regulations/[...id]`)는 기존 뷰어를 유지하되 셸 안으로: 상단에 기관·주제·시행일·버전 배지, 목차(조 목록) 사이드, 조문 본문, 오른쪽 관계(참조·관계도·판본 이력) 탭, "이 규정에 대해 묻기" 버튼(챗봇에 이 규정을 범위로 전달).

## 3. 주제별 비교 (`/topics`, `/topics/[topic]`)

- 주제 = 규정 제목·본문 기반 분류. 1차 분류 체계(설정 파일 `config/topics.yaml`): 회계·재무, 계약·구매, 인사, 복무, 보수·수당, 여비·출장, 연구관리, 연구윤리·보안, 기술사업화·지식재산, 감사·윤리·청렴, 안전·보건, 정보화·정보보호, 문서·기록, 직제·조직, 정관·이사회, 복리후생, 시설·자산, 교육·연수, 대외협력, 기타.
- 분류 방법: (1) 제목 키워드 규칙(설정의 `keywords`), (2) 규칙이 못 정하면 규정 제목+첫 조(목적) 임베딩과 주제 설명 임베딩의 유사도(bge-m3, 이미 있는 임베딩 서버), (3) 결과를 `regulation.work_topic(work_id, topic, score, method)`에 저장. 규정당 최대 2개 주제. 처리 파이프라인(`process_all` 이후)과 `reg topics classify [--all]` CLI로 갱신.
- `/topics/[topic]` 화면: 기관별로 묶은 규정 목록 (기관 25개 행 × 그 기관의 해당 주제 규정들), "없음" 기관 표시, 규정 2~4개를 골라 **나란히 비교**(같은 주제의 조문을 기관별로 나란히 — 조 제목 유사도로 짝짓기) → `/compare/topics?works=a,b,c`.
- 검색창에 "회계"처럼 주제 이름을 치면 주제 페이지로 바로 가는 제안을 띄운다.

## 4. 규정 도우미 — 검색과 질의응답 통합 챗봇 (`/assistant`)

### 4.1 백엔드: `POST /api/v1/chat` (스트리밍 SSE)
- 입력: `{messages: [{role, content}], institution?, scope?: {work_ids?: [], topic?}, as_of?}` — 대화 맥락(최근 6턴)을 받는다.
- 처리: 기존 `qa.service`의 분석 → 하이브리드 검색(OpenSearch `reg-provisions`, 임베딩) → 그래프 근거 확장 → 답변 생성(EXAONE) → 검증을 재사용한다. 의도 판별 결과에 따라:
  - **조문 찾기형**("천문연 여비규정 27조", "회계 관련 규정 보여줘"): 생성 없이 결과 카드 묶음(조문 카드, 기관별 묶음)과 한 줄 요약.
  - **질문형**("출장 다녀온 지 10일인데 증빙 안 냈어요"): 답변(결론·근거·설명·확인 필요) + 근거 조문 카드.
  - **비교형**("회계 규정 기관별로 비교해줘"): 주제 분류 + 기관별 해당 조문 카드 표.
  - **범위**: 기본은 전체 기관. 질문창 옆 범위 선택(전체 / 기관 여러 개)으로 좁히고, 질문에 기관 이름이 있으면 그 기관으로 자동으로 좁힌다. 전체 범위의 질문형 답변은 기관별로 다른 내용을 표로 묶어 보여 준다(예: 기관별 출장 증빙 제출 기한). 되묻기는 하지 않는다 (사용자 결정 2026-10-03).
- 스트림 이벤트: `status`(검색 중/근거 확장/답변 작성), `results`(카드), `answer_delta`(토큰), `answer`(최종 구조), `followups`(추천 후속 질문 3개), `done`. 실패 시 근거 카드만이라도 보낸다.
- 기존 `/api/v1/qa`, `/api/v1/hsearch`는 호환을 위해 유지(내부적으로 같은 서비스 호출). 질의 기록은 `ops.qa_log`에 대화 id와 함께 남긴다.

### 4.2 UI
- 챗봇 화면: 왼쪽 대화 목록(브라우저 저장), 가운데 대화(사용자 말풍선, 도우미 답변: 결론 강조 → 근거 인용(클릭 시 조문 팝업, 음영) → 설명 → 확인 필요/문의처), 결과 카드(기관 배지, 규정명 제N조, 맞은 항 강조, "규정 열기"), 추천 후속 질문 칩, 질문창 옆 범위 선택(전체 기관 / 기관 다중 선택 / 주제 / 특정 규정) — 앱 상단의 기관 선택기와 별개.
- 입력창: 예시 질문, 엔터 전송/Shift+엔터 줄바꿈, 스트리밍 표시, 중지 버튼.
- 기존 `/search`, `/qa`는 `/assistant`로 이동(redirect).

## 5. 검수 (`/review`)

- 백엔드 `GET /api/v1/review-tasks` 응답 보강: 기관(코드·이름), 규정 제목, 판본 시행일, 조문 위치(라벨), 원문 발췌, 문제 설명(종류별 한국어 문장), **해야 할 일**(종류별 행동 안내), 소관부서(ALIO `jidtDptm`이 있으면), 생성일, 담당자. 필터: 기관·종류·상태·담당자·검색, 페이지네이션, 기관별·종류별 집계.
- 처리 API: `POST /api/v1/review-tasks/{id}/assign {assignee}`, `POST /api/v1/review-tasks/{id}/resolve {decision, note}`, `.../dismiss {reason}` — 결정은 `decision` jsonb와 `resolved_at`에 남긴다. 사용자 식별은 아직 로그인이 없으므로 입력한 이름(브라우저 저장)을 쓴다.
- 종류별 안내 문구 예: REFERENCE "‘「상법」 제169조’ 인용의 대상 법령을 찾지 못했습니다 → 법령 적재 후 자동 재확인 / 오타면 올바른 이름 지정", PARSE "조문 구조를 읽지 못했습니다 → 원문 PDF와 비교해 확인", EFFECTIVE_DATE "시행일을 정하지 못했습니다 → 부칙에서 시행일 지정", CONFLICT, LOW_TEXT "글자가 거의 없는 문서(스캔본) → OCR 결과 확인".
- 화면: 기관별·종류별 요약 카드 → 표(기관 배지, 규정명·위치, 문제, 해야 할 일, 담당, 상태, 생성일) → 행 펼치면 원문 발췌·원문 PDF 링크·처리 버튼. 일괄 담당 지정.
- 법령 쪽(REFERENCE의 상당수는 law.go.kr 미적재 때문) 작업은 "법령 적재 대기" 상태로 묶어 기본 목록에서 접는다.
