# NST 규정·법령 인텔리전스 플랫폼 — 설계 스펙

- 작성일: 2026-10-01
- 상태: **초안, 검토 대기**
- 관련 문서: [PRD](../../PRD.md)
- 범위: 국가과학기술연구회(NST)와 소관 출연연의 내부규정 및 관련 법령을 수집·구조화·버전 관리하고, 다음 기능을 제공한다.
  - 규정 뷰어
  - 근거 기반 질의응답
  - 개정 영향 알림

## 1. 목표와 비목표

### 1.1 목표

1. NST와 출연연의 **현행 내부규정과 관련 법령**을 law.go.kr처럼 구조화해서 열람·검색할 수 있게 한다.
2. 연구자와 행정담당자가 자연어로 질문하면, **소속 기관 규정의 근거 원문을 먼저 보여주고** 그 근거 안에서만 설명한다.
3. 법령이나 규정이 바뀌면, 영향을 받는 내부규정 조항을 찾아 **규정별 담당자에게 자동으로 알리고** 검토 처리 결과를 기록한다.
4. 과거 버전을 보존해서, **특정 시점 기준 조회**와 신구 비교를 지원한다.

### 1.2 비목표 (이번 범위 아님)

- 법률 자문이나 개인 사안에 대한 최종 판단. 시스템은 근거 제시와 설명까지만 하며, 판단 책임은 소관부서에 있다.
- 비공개 내부규정 수집. ALIO에 공개된 것만 다룬다.
- 스캔 PDF의 OCR. 2차 범위이며, 스캔본은 검수 큐로 보낸다.
- 시행일·의무 주체·기한·금액을 담는 형식 온톨로지(OWL 등). 최소 개념 정의만 이번에 확정한다.
- 기관 자체 규정관리시스템과의 연계. 이후 확장할 수 있도록 수집기 인터페이스만 열어 둔다.

## 3. 전체 구성

```
┌──────────────── 외부 수집 구간 ────────────────┐
│ alio.go.kr (내부규정)   law.go.kr Open API (법령) │
│        └──────── 1. 수집기 ────────┘           │
│   원본 보관: Object Storage, SHA-256 키          │
│   해시 변경 = "변경 후보"일 뿐                    │
└──────────────────────┬─────────────────────────┘
                       ▼ 검증된 묶음 반입 (지금은 직접 연결, 향후 망연계로 교체)
┌──────────────── 내부 서비스 구간 ──────────────────────────────────────────┐
│ 2. 추출: HWP / HWPX / PDF → 공통 중간형식 · 보기용 PDF 생성                │
│ 3. 구조 파싱 + 참조 추출                                                    │
│ 4. 현행성·품질 검증 ── 불명확·충돌·품질 미달 ──▶ 검수 큐 (사람)            │
│ 5. PostgreSQL: 구조화 기준 데이터·버전·감사  +  outbox (같은 트랜잭션)      │
│       ├─▶ 6a. 청크·임베딩 워커 ─▶ OpenSearch (게시 버전별 인덱스 + 별칭)   │
│       ├─▶ 6b. 그래프 동기화 워커 ─▶ Neo4j (규정·조항 노드, 관계 + 메타)    │
│       └─▶ 6c. 게시 관리: 6a 완료 → 게시 버전 N 공개                        │
│                                                                             │
│ 7. 규정 API (조회·원문·비교·기준일·검수·담당자) ◀── 웹 UI (LLM 없이 동작) │
│ 8. Q&A 서비스: 게시 버전 N 고정 → 검색 → PG에서 근거 확장·검증 → 생성      │
│ 9. 개정 감지 (독립 스케줄): 신구 비교 → Neo4j 영향 탐색 → 담당자 알림      │
│ 공통: OIDC(Keycloak), 역할 기반 권한, 감사로그                             │
└─────────────────────────────────────────────────────────────────────────────┘
  추론 서버 (vLLM, OpenAI 호환): LLM · 임베딩 · 리랭커
```

**원칙**

- **현행만 노출하고 이력은 보관한다.** 화면과 답변의 기본값은 현행이지만, 모든 버전을 시행일과 함께 저장한다.
- **파생 저장소는 다시 만들 수 있어야 한다.** OpenSearch와 Neo4j는 언제든 PostgreSQL에서 전체 재구축할 수 있다.
- **근거 없는 답변은 하지 않는다.** 인용한 조항 ID, 인용 문구, 숫자가 원문과 일치할 때만 설명을 보여준다.
- **AI 계층은 선택 사항이다.** LLM이나 임베딩 서버가 멈춰도 열람과 키워드 검색은 동작한다.

### 4.1 실행 중인 nst-nexus 인프라 공유 (D-13)

|  | 원본 보관 S3 (전용 SeaweedFS) | `127.0.0.1:21066` |
|  | 예비 (워커 모니터링 등) | `:21062`, `:21063`, `:21067`~`:21069` |
| nst-nexus 공유 (호스트 포트) | PostgreSQL | `127.0.0.1:21055` |
|  | SeaweedFS S3 (전용, 공유 아님) | `127.0.0.1:21066` |
|  | Redis | `:21058` |
|  | Keycloak | 게이트웨이 `:21051/auth` |

|  | Mailpit SMTP | `mailpit:1025` |

- 내부 전용 서비스에 접근하려면, 이 프로젝트의 compose가 외부 네트워크 `nais_default`(`external: true`)에 참여해야 한다.
- 접속 정보는 전부 환경변수로 받는다. standalone 프로필에서는 같은 이름의 서비스를 자체적으로 띄운다.

**위험**: nst-nexus 개발 볼륨이 초기화되면 이 프로젝트의 데이터도 함께 사라진다.

- PostgreSQL은 정기적으로 `pg_dump --schema=regulation`으로 백업한다.
- 원본은 S3에, 파생 저장소는 재구축 경로로 복구한다.
- 이 저장소의 compose에 **전체 인프라를 단독으로 띄우는 프로필(`standalone`)**을 둔다.

### 4.3 기술 스택

nst-nexus와 같은 계열로 맞춰서 운영 부담을 줄인다.

- **그래프**: Neo4j 5 Community. 공식 Python 드라이버를 쓴다.

## 5. 데이터 모델

### 5.1 최소 개념 정의

| 개념 | 정의 |
|---|---|
| 기관 | 규정을 제정하는 주체. 예: NST, 한국천문연구원 |
| 규범문서 (Work) | 버전과 관계없이 하나로 식별되는 법령이나 규정 |
| 문서 종류 | 법률 / 시행령 / 시행규칙 / 행정규칙(고시·훈령·예규) / 내부규정 / 세부지침 |
| 버전 (Work Version) | 특정 시행일부터 효력을 갖는 규범문서의 판본 |
| 조항 (Provision) | 편·장·절·관·조·항·호·목, 별표·별지, 부칙의 단위 |
|  | · 논리적 ID는 버전이 바뀌어도 유지된다. |
|  | · 번호가 이동해도 본문 해시로 같은 조항임을 추적한다. |
| 관계 (Reference) | 조항이나 규범문서 사이의 연결. 아래 6가지 유형 |
| 담당자 | 규정별 소관부서와 담당 사용자 |

**관계 유형**

| 유형 | 의미 | 대표 문구 |
|---|---|---|
| `BASIS` | 이 조항의 법적 근거 | "법 제n조에 따라", "~에 근거하여" |
| `DELEGATION` | 하위 규정에 정할 권한을 넘김 | "따로 정한다", "세부사항은 ○○으로 정한다" |
| `IMPLEMENTS` | 위임받아 구체화함 (세부지침 → 모규정) | 규정명, 제정 근거 조항 |
| `MUTATIS` | 다른 조항을 그대로 적용(준용) | "~을 준용한다" |
| `EXCEPTION` | 다른 조항보다 우선함 (예외·단서) | "~에도 불구하고", "다만" |
| `CITATION` | 위 유형에 해당하지 않는 참조 | "~에 따른 ○○", "별표 1" |

### 5.2 식별자 (ELI 방식)


### 6.3 구조 파싱

- **머리부**: 규정명, 원규분류기호, 제정·개정 이력표 → `amendment_history`
- **단위 인식**
  - 장·절·관
  - `제\s*N\s*조(의\s*M)?\s*\((제목)\)`
  - 항 `①…⑳`, 호 `N.`, 목 `가.`

- **별표·별지**: 표 구조를 유지해서 `attachment`에 저장한다.
- **부칙**: 개정 차수별로 나눈다. 시행일 조항과 경과조치 조항을 표시한다.

### 6.4 참조 추출

| 문구 | 대상 해석 | 유형 |
|---|---|---|
| "제1항에도 불구하고", "전항", "같은 조" | 같은 규정, 상대 위치 | EXCEPTION / CITATION |
| "「회계규정」 제20조에 따른다", "회계규정에 따른다" | 같은 기관의 규정 (조항 또는 전체) | CITATION / BASIS |

### 6.5 현행성·품질 검증 (게시 여부를 결정하는 관문)

**내부규정 시행일 판정 (우선순위 순)**

1. 부칙의 "이 규정은 ○○부터 시행한다". "공포한 날부터"라고 되어 있으면 개정일을 쓴다.
2. 문서 안 개정 이력표의 마지막 개정일
3. ALIO `retryRvsnYmd`
4. 파일명의 날짜. 이 경우 `UNCERTAIN`으로 표시한다.

**처리 규칙**

- 1~3번이 서로 맞지 않으면 → `CONFLICT` 검수 큐
- 부칙에 "다만, 제○조는 ○○부터"가 있으면 → `effective_from_override`
- 시행일이 미래면 → `FUTURE`. 스케줄러가 시행일에 `CURRENT`로 바꾸고, 이전 버전의 `effective_to`를 닫는다.

**법령**: API가 주는 시행일과 조문시행일을 그대로 쓴다.

**품질 검사** (하나라도 실패하면 게시하지 않고 검수 큐로)

- 조 번호 연속성. 빠진 번호에는 `삭제` 주석이 있어야 한다.
- 항·호 순서
- **목차의 조 목록과 본문의 조 목록이 일치하는지** (목차가 있는 경우)
- 원문 글자 수 대비 추출된 글자 수 비율
- 해석하지 못한 참조의 비율이 기준을 넘지 않는지

### 6.6 버전 적재

- world_law_collect의 `loader.py` 방식으로 적재한다.
  - 직전 버전과 조항 단위로 비교한다.

## 7. 동기화와 게시 버전

- **outbox 기록**: PostgreSQL 변경과 outbox 기록은 같은 트랜잭션에서 한다.
- **relay**: 미처리 이벤트를 `FOR UPDATE SKIP LOCKED`로 가져와 Dramatiq 작업으로 넘긴다.
- **소비자의 멱등성**: 소비자는 `(event_id)` 처리 기록으로 중복을 걸러낸다. 같은 work의 이벤트는 `work_id` 기준으로 순서를 보장한다.
- **게시 절차**
  1. `release`를 BUILDING으로 만든다.
  2. 새 인덱스 `nais-regulations-r{N}`을 만든다.
     - 변경된 work는 새로 청크를 만들고 임베딩한다.
     - 변경되지 않은 청크는 이전 인덱스에서 복사한다. (reindex)
  3. 검증 쿼리를 통과하면 **별칭을 원자적으로 전환**하고 PUBLISHED로 바꾼다.
- **답변 시점의 고정**: Q&A는 요청을 시작할 때 별칭이 가리키는 `release_id`를 고정한다. 근거 확장도 `release_item` 범위 안에서만 한다.
- **Neo4j**: 같은 이벤트를 받아 갱신하며, `release_id`를 속성으로 기록한다. 답변 경로가 아니므로 늦게 반영돼도 서비스 정합성에 영향이 없다. (D-05)
- **임베딩 서버 장애**: 임베딩 작업은 큐에 남겨 재시도한다. 게시는 BM25 필드만 갖춘 상태로도 진행할 수 있고, 이때 `embedding_status`를 표시한다.

| `EmbeddingProvider` | `:8002/v1/embeddings`, bge-m3 (1024차원) | 같음 |
| `RerankProvider` | `:8003/rerank`, bge-reranker-v2-m3 | 같음 |

- 2026-10-01 점검 결과 (Windows 로컬)
  - 임베딩 1024차원 정상
  - 리랭크에서 정산 조문이 1위
  - EXAONE이 JSON 스키마를 지켜서 응답, 1.2초
- 모델과 엔드포인트는 환경변수로 바꾼다.

### 8.2 처리 흐름

1. **질의 분석** (LLM, JSON 스키마)
   - 출력 항목: `institution_mention`, `as_of_date`, `question_type`(기한 / 금액 / 가능여부 / 절차 / 정의 / 기타), `concepts`, `expanded_terms`
   - 용어 확장 예: 지출결의 → 정산·증빙·여비 신청
   - 동의어 사전을 먼저 적용하고, LLM 확장은 보조로 쓴다.
2. **기관 확정**
   - 우선순위: 질문에 나온 기관 → `user_profile.institution_id`
   - 기관이 없거나 둘이 서로 다르면 **답하지 않고 되묻는다.** 예: "어느 기관 규정 기준으로 볼까요?"
3. **기준일 확정**
   - 질문에 날짜가 있으면 그 날짜, 없으면 오늘(현행)
   - 기준일 이후에 개정이 있었다면 응답에 표시한다.
4. **검색**
   - 하이브리드(BM25 + kNN, 점수 정규화 결합)로 검색한다.
   - 필터: 해당 기관의 규정 + 관련 법령, 기준일에 유효한 버전
   - 상위 50건을 뽑아 리랭커로 최종 8건을 남긴다.
5. **근거 확장** (PostgreSQL, 고정된 release 안에서)
   - 해당 조 전체
   - 그 조를 대상으로 하는 `EXCEPTION`
   - 그 조가 가리키는 `CITATION` / `MUTATIS` / `BASIS` 대상 (1단계)
   - 참조된 별표
   - 최근 개정 정보와 부칙의 경과조치
6. **답변 생성** (LLM, JSON 스키마)

   ```json
   {
     "결론": "미충족 | 충족 | 조건부 | 판단불가",
     "근거": [{"pv_id": "...", "인용": "원문 구간"}],
     "설명": "...",
     "확인_필요": ["..."],
     "문의처": "소관부서"
   }
   ```

   **계산할 수 있는 판정은 코드로 한다.**
   - 대상은 질문 유형이 기한·금액·횟수인 경우다.
   - LLM은 값만 뽑는다. 근거에서 `기준값`(예: 기한 7일, 상한 금액)을, 질문에서 `사실값`(예: 경과 10일)을 정수나 금액으로 꺼낸다.
   - 결론(미충족 / 충족)은 코드가 비교해서 정한다.
   - 근거 (2026-10-01 점검)
     - 선택지 이름을 바꾼 뒤에도 EXAONE-7.8B는 3번 중 2번을 "조건부"라고 잘못 판정했다.
     - 설명에는 "10일 경과, 미제출"이라고 정확히 썼다.
     - 즉 값 추출은 맞았는데 판정이 틀렸다.
   - 출력 안정성: 구조화 출력에서 불필요한 공백이 반복되다가 토큰 한도에서 잘려 JSON이 깨진 사례가 1번 있었다.
     - 출력 토큰 한도를 넉넉하게 잡는다.
     - 공백을 막는 구조화 출력 옵션을 쓴다.
     - 파싱에 실패하면 다시 생성한다.
7. **검증** (코드로 처리)
   - 인용한 `pv_id`가 제공된 근거 집합 안에 있는가
   - `인용`이 원문에 정확히 들어 있는가 (공백 정규화 후 부분 문자열 비교)
   - 설명에 나온 **숫자(일수·금액·비율)가 인용 원문에 있는가**
   - **결론과 설명이 서로 맞는가**: 결론별 금지 표현을 규칙으로 검사하고, 필요하면 LLM 자기검증을 한 번 더 한다.
     - 예: 결론이 "충족"인데 설명에 "위반"이 있으면 실패
     - 2026-10-01 점검에서 실제로 일어난 결론·설명 불일치를 반영한 항목이다.
   - 실패하면 한 번 다시 생성한다. 그래도 실패하면 **근거 조문만 보여주고** "자동 설명을 만들지 못함"을 표시한다.
8. **응답 화면**
   - 근거 원문 카드를 먼저 보여준다. 카드에는 "YYYY-MM-DD 시행본 기준"과 출처(ALIO 게시일 / law.go.kr)를 표시하고 "원문 보기" 버튼을 둔다.
   - 그다음 설명과 확인 필요 사항을 보여준다.
   - 마지막에 "법적 판단이 아니며 소관부서 확인 필요" 안내와 문의처를 붙인다.

### 8.3 답하지 않는 기준

- 리랭크 점수가 임계값 미만이면 → "관련 규정을 찾지 못했습니다"와 함께 후보 조문 목록을 보여준다.
  - 임계값은 M4에서 "답할 수 없는 질문" 정답셋으로 정한다.
  - 정답셋 평가 전까지는 bge-reranker 점수 0.3을 임시값으로 쓴다.
- 근거가 `CONFLICT`이거나 검수가 끝나지 않은 버전이면 → "판단불가"로 답하고 이유를 표시한다.
- 개인 분쟁·징계처럼 판단이 필요한 사안이면 → 관련 조문과 문의처만 안내한다.
- 기관을 정할 수 없으면 → 되묻는다.

### 8.4 대표 시나리오 (평가셋 1번 문항)

> 질문: "천문연 소속인데 출장 다녀온 지 10일 지났고 지출결의를 아직 안 했어요. 문제가 없을까요?"

- 기관: 한국천문연구원
- 근거
  - 여비규정 **제27조①**: 출장 종료일 다음 날을 기점으로 **7일 이내**에 증빙서를 회계담당부서에 제출
  - 제4조의2: 여비의 정산
- 결론: **미충족** (증빙 제출 기한 7일 경과)
- 확인 필요
  - "지출결의"는 규정에 없는 용어다. 증빙 제출·정산 절차와 같은 것인지 확인이 필요하다.
  - 기한을 넘겼을 때의 불이익 조항은 찾지 못했다.
- 비교 사례: 같은 질문이라도 NST 여비규정 제9조의2는 국내출장 **10일 이내** 정산 신청이다. **기관 확정이 왜 필요한지 보여주는 사례**다.

### 8.5 장애 시 동작과 기록

| 상황 | 동작 |
|---|---|
| LLM 장애 | 검색 결과와 원문만 보여준다. |
| 임베딩 장애 | BM25만으로 검색한다. |
| 리랭커 장애 | 하이브리드 점수 순서를 그대로 쓴다. |

모든 질의는 `qa_log`에 남긴다. 사용자 피드백(도움됨 / 아님 + 사유)을 받는다.

## 9. 개정 감지 · 영향 분석 · 알림

### 9.1 무엇이 바뀌면 처리하나

| 출처 | 영향받는 대상 |
|---|---|
| **법령 개정** (law.go.kr, 매일 확인) | 그 법령을 근거·위임·준용·참조하는 내부규정 조항 |
| **내부규정 개정** (ALIO) | 그 규정을 참조하는 같은 기관의 다른 규정·세부지침 |
| **시행일 도래** | FUTURE 버전. 시행 30일 전과 7일 전에 미리 알린다. |

### 9.2 처리 흐름 (Q&A와 독립적으로 동작)

1. **변경 확정**
   - 해시 변경은 후보일 뿐이다.
   - 검증을 통과한 `provision_change` 중 `ANNOTATION_ONLY`를 뺀 것만 다음 단계로 넘긴다.
2. **영향 탐색** (Neo4j, 기준일 = 변경 시행일)
   - 바뀐 조항이나 규범문서로 들어오는 관계를 거꾸로 따라간다.
   - 규정 전체를 참조하는 관계도 포함한다.
   - 위임 사슬(`DELEGATION` / `IMPLEMENTS`)은 최대 2단계까지 따라간다.
3. **영향 유형과 심각도**

   | 영향 유형 | 심각도 |
   |---|---|
   | 참조 대상이 삭제됨 | 높음 |
   | 근거·위임·준용 대상의 내용 변경 | 높음 |
   | 참조 대상의 번호 이동 (내부규정 조문 수정 필요) | 중간 |
   | 단순 참조 대상의 내용 변경 | 중간 |
   | 관련 법령에 조문 신설 (의미 검색으로 후보만 제안) | 낮음, 참고용 |

4. **검토 요약** (LLM이 켜져 있을 때만)
   - 신구 조문 비교 요약과 영향 조항별 검토 포인트를 만든다.
   - 8.2의 검증을 똑같이 적용한다.
   - LLM이 꺼져 있으면 diff만 보낸다.
5. **알림**
   - `change_impact`를 만들고 `owner_assignment`의 담당자에게 보낸다.
   - 채널: 앱 내 알림 + 메일
   - 담당자별로 하루 1회 묶음 알림을 보낸다. 심각도 "높음"은 즉시 보낸다.
   - 담당자가 지정되지 않은 규정은 기관 관리자에게 보낸다.
   - 멱등 키는 `(원인 변경 ID, 영향 조항 ID)`다.
6. **검토 처리 흐름**
   - 상태는 `NEW → ACKED → ACTION_REQUIRED | NO_ACTION(사유 필수) → RESOLVED` 순서로 바뀐다.
   - 해당 내부규정의 새 버전이 수집되면 `resolved_by_version_id`로 자동 연결한다.
   - 기한(기본 14일)을 넘기면 기관 관리자에게 다시 알린다.
   - 모든 상태 변경은 감사로그에 남긴다.

## 11. 보안 · 권한 · 감사

- **인증**: Keycloak `nais` realm OIDC. 클라이언트는 `regulation-web`, `regulation-api`다.
- **역할**

  | 역할 | 권한 |
  |---|---|
  | `REG_VIEWER` | 열람·질의 (기본) |
  | `REG_OWNER` | 규정 담당자. 알림 처리 |
  | `REG_REVIEWER` | 검수 |
  | `REG_ORG_ADMIN` | 기관 관리자 |
  | `REG_ADMIN` | 플랫폼 관리자 |

  역할과 소속 기관은 `user_profile`과 Keycloak 클레임으로 정한다.
- **데이터**: 대상이 공개 규정이므로 열람 제한은 없다. 알림, 검수, 질의 로그는 기관 범위로 제한한다.
- **질의 개인정보**: 입력 안내 문구를 둔다. 주민번호, 전화번호, 이메일 패턴은 마스킹한 뒤 저장한다.
- **감사**: 게시, 검수 결정, 담당자 지정, 알림 처리, 관리 설정 변경을 `audit_event`에 append-only로 남긴다. `qa_log`에는 모델과 게시 버전을 기록한다.
- **추론 서버**: 내부망 IP로 접근을 제한한다. Windows 방화벽에서 플랫폼 서버만 허용한다. 운영 시 vLLM `--api-key`를 쓴다.

## 12. 평가

### 12.1 정답셋

| 정답셋 | 규모 | 만드는 방법 |
|---|---|---|
| 구조 파싱 | 5개 기관 × 규정 10건 | 조·항·호·목 경계, 시행일, 참조를 손으로 표시 |
| 질의-근거 | 200개 이상 | 여비, 연구비, 인사, 계약, 보안 등 분야별로 만들고, 8.4 시나리오를 포함한다. |

| 개정 영향 | 과거 실제 개정 사례 | **버전 이력으로 과거 개정을 다시 재생해서 사후 검증한다.** |

### 12.2 지표와 초기 목표 (평가하면서 조정)

| 영역 | 지표 | 목표 |
|---|---|---|
| 수집·파싱 | 조·항·호 경계 F1 | ≥ 0.97 |
|  | 시행일 판정 정확도 (자동 판정 건) | ≥ 0.95 |
|  | 참조 추출 정밀도 / 재현율 | ≥ 0.95 / ≥ 0.90 |
| 검색 | Recall@10 / nDCG@10 (하이브리드, BM25, 벡터 비교) | ≥ 0.90 / ≥ 0.75 |
| 답변 | 인용 정확도 | ≥ 0.90 |
|  | 결론 정확도 | ≥ 0.85 |
|  | 숫자 일치율, 결론·설명 일관성 (검증 단계에서 강제) | 1.00 |
|  | 답할 수 없는 질문을 "판단불가"로 처리한 비율 | ≥ 0.90 |
|  | 기관이 없을 때 되묻는 비율 | 1.00 |
| 개정 알림 | 영향 탐지 재현율 / 정밀도 | ≥ 0.95 / ≥ 0.80 |
|  | 서식 변경만으로 보낸 오탐 알림 | 0건 |
|  | 공포부터 알림까지 걸린 시간 | ≤ 1일 |
| 성능 (개발, RTX 4090) | p95 검색 / 답변 | < 1초 / < 10초 |
| 사용자 | "도움됨" 비율, 담당자 검토 처리 시간 | 기준선 측정 후 설정 |

- 평가 실행기는 저장소 안에 둔다. (`eval/`)
- 게시 버전과 모델이 바뀔 때마다 실행하고 결과를 기록한다.

## 14. 위험과 대응

| 위험 | 대응 |
|---|---|
| ALIO 게시가 실제 개정보다 늦거나 빠질 수 있음. 표본의 최신 개정일이 2023~2024년에 몰려 있었다. | · 답변에 "ALIO 게시 기준"과 게시일을 표시한다. |
|  | · 기관 자체 시스템과 연계할 수 있도록 수집기 인터페이스를 열어 둔다. |

|  | · 운영은 더 큰 모델을 목표로 한다. |
| 공유 인프라(nst-nexus 개발 볼륨) 의존 | 스키마 단위 백업, 재구축 경로, standalone 프로필 |

|  | · 상태 확인 결과를 운영 화면에 표시한다. |
|  | · 운영은 서버 GPU로 옮긴다. |

## 15. 미결 사항

1. 파일럿 기관 4곳(NST, 천문연, KIST, ETRI)을 확정하고 출연연 전체 목록과 ALIO 기관명을 매핑한다. ETRI는 표본 조회에서 "여비" 규정이 검색되지 않아 규정명 확인이 필요하다.
2. law.go.kr Open API OC 키 발급과 사용 한도를 확인한다.
3. nst-nexus OpenSearch 이미지에 k-NN과 neural-search 플러그인이 있는지 확인한다. 없으면 이미지를 확장하거나 별도 노드를 둔다.
4. 연구행정 핵심 법령 시드 목록을 확정한다.
5. 담당자 지정의 초기 데이터 출처를 정한다. (기관별 수기 등록 / CSV 업로드)
